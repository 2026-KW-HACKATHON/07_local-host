# 점주 UI 구현 및 백엔드 연결 요구사항

갱신일: 2026-10-08. 비교 기준은 `origin/backend-a: 4a973fe`, `origin/backend-b: ab36c09`와 현재 로컬 통합 백엔드의 Controller/DTO다.

이번 작업은 사용자가 승인한 **프론트 UI와 기기 내 저장** 범위다. 백엔드 계약이나 서버 코드를 변경하지 않았다. 쿠폰 발행·포인트·사용 처리는 같은 기기의 점주/손님 계정 사이에서 동작하며, 실제 서버 게시·다른 기기와의 동기화·실제 결제 처리를 완료했다는 뜻은 아니다.

## 이번 점주 피드백 반영 범위

- 등록 전 안내 화면을 제거하고, 관리할 식당이 없는 점주는 바로 **1단계 식당 정보 입력**으로 진입한다.
- 헤더의 식당 변경 버튼을 제거한다. 로그아웃은 **My 첫 화면 오른쪽 위**에만 둔다. 이 변경으로 기존 서버의 식당을 삭제하거나 소유권을 바꾸지 않는다.
- 1단계는 이름·주소, 하나의 **영업시간** 영역 안의 시작/종료 입력, 정기 휴무일 선택으로 구성한다.
- 식당 이름으로 검색하면 앱 안에서 네이버 지도 검색 결과를 연다. 검색에서 주소를 확인한 뒤 등록 화면에 직접 입력한다. 자동 주소 선택이나 네이버 장소와 밥줄 식당의 자동 연결은 구현 범위가 아니다.
- 식당 등록 후 문구는 “이어서 단계별 프로모션을 입력해주세요.”로 변경한다. 2단계와 My의 버튼은 “저장”이며, “초안” 표시와 별도 저장 완료 알림을 제거한다.
- 제보 화면은 “최근 30분 제보 N건” 집계 칸 대신 **최신순 개별 내 제보 목록**을 표시한다. 화면에는 “내가 작성한 제보”로 표시하며, 현재 구현의 저장 범위는 기기 안의 해당 점주 계정이다.
- 점주가 혼잡도를 제출할 때 추가 설명을 작성할 수 있다. 혼잡도는 기존 서버 API로 전송하고, 설명은 성공한 제보 응답과 함께 기기에 보관한다.
- 프로모션 수정은 제목 옆 버튼 하나로 통합한다. 별도의 할인 프로모션 등록 폼과 단계별 수정 버튼은 제거한다.
- 각 단계의 회색 혜택 박스 아래에서 발행 조건을 설정해 프로모션을 진행하거나 중지한다. 기존의 단순 진행 상태 토글을 **쿠폰 발행 조건과 발행 기록**으로 교체한다. 여러 단계의 동시 진행을 허용하며, 진행한 혜택은 제보 화면과 같은 기기의 손님 화면에 반영한다.
- 발행 조건에는 게시 종료일/종료일 없음, 사용 요일/요일 제한 없음, 시간 구간/시간 제한 없음, 쿠폰 비용을 입력한다. 여러 시간 구간과 자정을 넘는 시간 구간을 지원하며 겹친 구간은 저장 전에 검사한다.
- 데이터는 **최근 4주만** 표시한다. 요일을 선택하면 0~23시 시간별 막대를 가로 스크롤로 확인한다. 막대 위 숫자는 표시하지 않는다.
- My에서 **영업시간 수정은 시간만**, **식당 위치 수정은 검색/주소만** 입력한다. 변경하지 않는 식당 이름·주소·시간은 기존 서버 값을 보존한다.
- 영업 변경 사항은 날짜 선택 → 휴무/영업 선택 → 영업하는 경우 시작/종료 시간 입력 → 저장으로 구성한다. 자유 형식 변경 내용과 입력 내용 비우기 버튼을 제거한다.
- 손님의 제보 식당 검색 목록과 선택 화면에 영업 중/영업 종료 및 영업시간을 표시한다. 아래의 영업 일정 제한이 적용된다.

앱은 390×844 기준의 React Native 네이티브 화면이며 입력·탭·버튼은 실제 컴포넌트다. 사용자 제공 워드마크와 marketing/point/person/data SVG에서 만든 자산을 계속 사용한다. 이번 피드백 작업은 새로운 Figma 측정이나 픽셀 단위 원본 일치 완료를 의미하지 않는다.

## 서버에 반영되는 항목과 기기에만 저장되는 항목

### 기존 서버에 연결되는 기능

- 식당 목록/등록/수정: GET/POST `/api/restaurants`, PUT `/api/restaurants/{id}`. 로그인 점주의 `ownerId`와 일치하는 매장만 사용한다.
- 점주 혼잡도 제보: POST `/api/restaurants/{id}/crowd`, 현재 요청 본문은 `{ level }`뿐이다. 성공 응답의 제보 ID·식당 ID·사용자 ID·시각을 기기 내 목록의 기준으로 사용한다.
- 기존 서버 프로모션 조회: GET `/api/restaurants/{id}/promotions/manage`. 현재 유효한 서버 혜택은 제보 화면에서 별도로 확인할 수 있다.
- 실제 이메일 회원가입/로그인 및 OWNER 역할에 따른 진입을 유지한다. 시연용 계정 우회나 권한 우회는 없다.

기존 퍼센트 할인 생성/수정/삭제 API는 백엔드에 그대로 있다. 이번 점주 UI에서 해당 등록 폼을 제거한 것이며, 서버에 저장된 프로모션을 삭제한 것은 아니다. 단계별 무료 서비스 혜택을 임의의 할인율로 변환해 이 API에 보내지 않는다.

### 기기 내 저장

- **단계별 혜택, 정기 휴무일, 날짜별 영업 변경**: 서버 주소·사용자 ID·식당 ID별로 구분하여 SecureStore에 저장한다. 기존 저장 키와 설정을 보존한다. 예전 진행 토글 상태만으로 쿠폰을 자동 발행하지 않으며, 저장된 혜택 문구를 유지한 채 발행 조건을 새로 확인한다.
- **프로모션 발행 기록·손님별 포인트 지갑·받은 쿠폰**: 앱 문서 영역의 `device-coupons/{서버 범위}/state.json`에 저장한다. 같은 서버를 바라보는 같은 앱 설치 안에서는 점주 발행을 손님 계정이 조회할 수 있다. 지갑은 사용자 ID와 정규화한 이메일로 분리하며, 다른 서버/다른 손님 계정의 잔액·쿠폰을 공유하지 않는다.
- **점주 본인의 성공한 제보와 추가 설명**: 같은 서버/사용자/식당 범위의 앱 문서 영역에 제보 ID별로 저장한다. 다른 사람의 제보나 다른 기기의 과거 제보를 생성해서 표시하지 않는다.
- 추가 설명은 최대 200자다. 현재 서버 요청에 포함하지 않으므로 손님 또는 다른 기기에 공유되지 않는다.
- 날짜별 영업 변경은 현재 선택한 날짜의 한 건을 보관한다. 새 날짜의 변경 사항을 저장하면 이전의 해당 설정을 대체한다. 복수 날짜 일정 관리가 필요하면 서버 계약과 목록 UI를 함께 정해야 한다.
- 앱을 다시 열 때 기기 저장 내용을 조회하지만 다른 기기와 동기화하지 않는다. 앱 데이터 삭제/재설치 후 복원을 보장하지 않으며, 서버 연결 시 자동 업로드하지 않는다.
- 프로모션의 “진행 중”과 쿠폰 다운로드·사용 완료는 현재 **기기 내 처리 결과**다. 같은 기기의 손님 계정에서 다운로드할 수 있지만 다른 휴대폰의 손님에게 서버로 게시되는 것은 아니다. 기존 서버의 퍼센트 할인 안내만으로 쿠폰을 만들지 않는다.
- 잘못되거나 손상된 기존 저장값을 빈 값으로 취급해 덮어쓰지 않는다. 서버 제보 성공 후 기기 저장만 실패했다면 재제보를 유도하지 않고 저장 실패를 별도로 알린다.
- 포인트 차감과 쿠폰 생성은 하나의 상태로 저장한다. 모든 읽기/수정 요청을 직렬화하고 임시 파일 저장 후 교체하여, 저장 실패 시 차감만 남거나 사용 처리만 완료되는 것을 방지한다. 잔액과 거래 내역의 일치 여부도 검사한다.

## 확정한 쿠폰·포인트 정책

- 손님 지갑을 처음 생성할 때 **1,000P를 한 번** 지급한다. 앱 재진입·재로그인마다 다시 지급하지 않는다. 점주 계정에는 손님 지갑을 생성하지 않는다.
- 성공한 손님 제보의 서버 응답을 받은 뒤 **제보 ID당 1,000P를 한 번** 기기 지갑에 적립한다. 현재 백엔드가 적립한 것이 아니며 서버 제보 저장과 기기 적립은 별도 처리다. 기기 저장 실패·앱 종료와 같은 경계를 서버 거래로 보장하려면 별도 계약이 필요하다.
- 점주는 쿠폰 비용을 **최소 500P, 500P 단위의 양의 정수**로 설정한다. 임의의 3,000P 상한은 두지 않는다. “1P = 1원”은 혜택 설계상의 환산 기준이며, 결제·현금 환급·실제 혜택 가격이 검증됐다는 의미가 아니다.
- 다운로드에는 식당 근처에 있어야 한다는 조건이 없다. 사용 요일·시간 밖에서도 게시 중인 프로모션을 다운로드할 수 있다. 다운로드 시 게시 유효성, 잔액, 중복 보유 여부를 검사한다.
- 쿠폰은 다운로드 시각부터 **정확히 72시간** 유효하다. 게시의 **종료일 없음** 옵션과 쿠폰의 72시간 만료는 별개다. 게시 종료일은 한국 시간의 해당 날짜까지 적용한다.
- 같은 발행 프로모션의 **미사용·미만료 쿠폰을 이미 보유**했다면 추가 쿠폰을 만들거나 포인트를 차감하지 않는다. 기존 쿠폰을 사용했거나 만료된 뒤에는 게시가 여전히 유효한 경우 다시 다운로드하고 비용을 다시 차감할 수 있다.
- 받은 쿠폰은 혜택 문구·사용 요일/시간·포인트 비용을 다운로드 당시 조건으로 보존한다. 점주가 게시를 중지하거나 게시 종료일이 지나도 이미 받은 쿠폰은 72시간 안에서 기존 사용 조건대로 유효하다. 중지/종료는 **새 다운로드와 재다운로드만 차단**한다.
- 쿠폰 사용 시 미사용 여부·72시간 만료·보존된 요일/시간을 검사한다. 게시 종료일은 받은 쿠폰의 사용 기한으로 다시 적용하지 않는다. 사용된 쿠폰을 다시 사용할 수 없다. 사용에 GPS 제한이나 새로운 점주 인증 규칙을 임의로 추가하지 않는다.
- 현재 기기 시각을 이용한 로컬 기능이다. 기기 시간 조작 방지, 다른 기기 동시 사용, 점주의 실제 사용 승인, 실제 매장 결제는 서버와 확인할 항목이다.

## 최근 4주 데이터의 정확한 의미

현재 화면의 데이터 범위는 **이 기기에 저장된 해당 점주 본인의 성공한 제보**다. 전체 매장의 손님·점주 제보를 포함하는 서비스 분석이 아니다. 화면에는 개발용 저장 범위를 노출하지 않고 “내가 작성한 제보 기준”으로 표시한다.

- 최근 28일 이내의 유효한 제보를 한국 시간(`Asia/Seoul`)의 요일·한 시간 단위로 묶는다.
- 여유 `AVAILABLE = 0`, 보통 `FEW_SEATS = 1`, 혼잡 `LONG_WAIT = 2` 중 **제보 수가 가장 많은 상태**를 선택한다. 평균 점수나 평균을 반올림한 상태가 아니다.
- 최다 제보 수가 같으면, 동률 상태 중 **가장 최근 제보 상태**를 선택한다. 원본 시각도 완전히 같아서 순서를 판단할 수 없으면 임의로 선택하지 않는다. 서버 연동 시 제보 ID 등 동일 시각의 추가 순서 기준을 합의한다.
- 미래 시각, 잘못된 시각, 28일 밖의 제보와 `UNKNOWN`을 제외한다. 제보가 없는 시간과 여유 `0`을 구분하며, 여유는 초록색 기준선 표시로 보인다.
- 데이터가 없으면 “최근 4주에 작성한 제보가 없어요.”를 표시한다. 원본 데이터가 연결되지 않은 상태와 조회 결과가 실제로 빈 상태도 구분한다.
- 기존 점주 화면의 **최근 7일 버튼과 평균/선 그래프는 이번에 제거**했다. 기존 차트 API의 최대 범위는 여전히 168시간이다. `hours=672`를 임의로 요청하거나 7일 데이터를 4주 분석으로 표시하지 않는다.

## 손님에게 표시되는 영업 정보의 제한

손님 화면의 영업 중/영업 종료는 서버 식당 응답의 `openingTime`/`closingTime`과 현재 한국 시간을 비교한 값이다. 자정을 넘는 영업시간은 다음날 종료로 표시하고, 시작/종료가 같아 24시간 영업인지 휴무인지 구분할 수 없는 경우 확인 필요로 표시한다.

점주 기기에만 저장한 정기 휴무·특정 날짜 휴무/영업 변경은 손님 계정에 공유하지 않는다. 따라서 현재 표시에는 기본 영업시간 외의 예외 일정이 반영되지 않는다. 이를 실제 영업 여부의 확정 정보로 사용하려면 다음 영업 일정 계약이 필요하다.

## 백엔드 팀과 협의할 계약

구체적인 경로와 DTO는 아래 요구사항을 합의한 뒤 확정한다. 존재하지 않는 API를 프론트에서 임의로 만들지 않는다.

### 1. 단계별 서비스형 프로모션

- 식당별 1~3단계, 발행 ID/버전, 혜택 문구, 게시/중지 상태, 게시 종료일 또는 종료일 없음, 사용 요일·복수 시간 구간/제한 없음, 쿠폰 비용과 손님 공개 상태가 필요하다. 퍼센트 할인과 무료 서비스형 혜택을 구분한다.
- 여러 단계 동시 진행을 허용할지, 한 단계만 진행할지 서버의 최종 규칙을 확정한다. 현재 프론트는 단계별 독립 진행/중지이며 다른 단계를 자동 종료하지 않는다.
- 진행/중지 요청의 소유권 검증, 중복 요청 방지, 게시 종료 처리, 재조회 일관성을 제공한다. 현재 기기 구현은 같은 단계가 이미 진행 중이면 동일 요청은 기존 발행을 반환하고, 조건이 다른 요청은 기존 발행 중지 후 새 발행을 요구한다. 받은 쿠폰의 조건을 소급 변경하지 않는다.
- 사용 요일/시간은 한국 시간 기준으로 저장·평가하고, 자정 넘김·시간 구간 겹침·시작 포함/종료 제외 경계를 서버와 일치시킨다. 종료일 없는 게시와 72시간 쿠폰 만료를 별도 필드로 다룬다.
- 서버 지갑·거래 내역·발급 쿠폰 모델이 필요하다. 초기 지급과 제보 보상은 사용자/제보 ID 기준으로 중복을 방지하고, 차감과 발급·쿠폰 사용은 서버에서 원자적으로 처리한다. 동시 요청·재시도·응답 유실 시 동일 거래 결과를 반환하는 멱등성 계약을 정한다.
- 사용 시 손님 확인 버튼만으로 완료할지 점주 확인/코드/QR 등의 승인이 필요한지 합의한다. 현재 로컬 사용 버튼은 실제 점주 승인이나 매장 결제의 증거가 아니다. 서버 시간·서명된 발급 정보·소유권 검증으로 다른 기기의 중복 사용을 방지해야 한다.
- Figma의 제보 기반 추천/게시 승인 기능을 제공한다면 추천 ID·근거·관측 기간·단계·수락/거절·중복 승인 방지와 알림 진입 계약이 별도로 필요하다. 기기 상태 전환으로 승인/쿠폰 게시가 완료된 것으로 간주하지 않는다.
- 이미 저장한 기기 설정을 서버로 이전할 때 사용자 확인·충돌 처리·중복 생성 방지 방식을 정한다.

### 2. 영업 일정 및 손님 조회

- 기본 영업시간, 정기 휴무 요일, 특정 날짜의 휴무/영업 및 시작·종료 시간을 저장·조회해야 한다. timezone, 자정 넘김, 24시간 영업, 시작=종료 처리도 명시한다.
- 임시 일정과 정기 휴무/기본 시간의 우선순위 및 복수 날짜 일정 변경·삭제 방식을 합의한다.
- 손님에게도 동일한 일정 또는 계산된 현재 영업 상태/다음 영업시간을 제공한다. 점주 기기 저장값을 다른 사용자에게 직접 공유하는 방식으로 대체하지 않는다.
- 식당 조회 응답/수정 응답의 동시 갱신과 오래된 수정값 충돌 처리 방식을 확인한다.

### 3. 최신순 제보 목록과 추가 설명

- 식당별 손님·점주 제보 목록에 제보 ID, 표시 닉네임/역할, 혼잡도, 시각, 추가 설명과 페이지 정보를 제공한다. 최신순 정렬과 같은 시각의 안정적인 정렬 기준이 필요하다.
- 제보 생성 시 추가 설명을 받는 필드, 길이/내용 검증, 공개 범위와 수정 가능 여부를 정한다. 현재 프론트의 로컬 설명을 서버가 이미 보관한다고 간주하지 않는다.
- 인증·매장 소유권을 검증한다. 손님 GPS 체류 증명과 점주 제보 예외를 서버에서 구분하며, 프론트 버튼 제한만으로 권한을 보장하지 않는다.
- 서버의 제보 내역과 기기에 저장된 동일 ID 내역을 중복 표시하지 않는 병합 기준이 필요하다.

### 4. 매장 전체의 4주 최빈 혼잡도 분석

- 최근 28일의 시작/종료 범위·timezone을 명시하고, 한국 시간 기준 요일 × 24시간 단위로 `AVAILABLE`/`FEW_SEATS`/`LONG_WAIT`별 제보 수를 제공한다. 또는 동일 집계가 가능한 원시 제보를 완전하게 조회할 수 있어야 한다.
- 단순한 시간별 평균 점수는 최빈값 복원에 사용할 수 없다. 최대 상태가 동률인 경우를 위해 상태별 최신 제보 시각 또는 서버에서 결정한 최종 상태/동률 기준도 필요하다.
- 제보 없는 시간은 `null`/별도 상태와 표본 수 0으로 표현하여 여유 0과 구분한다. 표시 범위가 전체 매장인지 필터된 보고자인지 응답에 명확하게 한다.
- 현재 최대 168시간 제한을 유지한 채 4주 화면을 완성했다고 판단하지 않는다. 범위 확장 또는 별도 분석 계약을 확정한다.

### 5. 네이버 검색 및 식당 식별

- 현재는 앱 내 네이버 지도 검색 화면이다. 검색 결과의 자동 선택/입력, 밥줄 식당 중복 검사, 위치·층 연결이 필요하면 서버 검색 프록시와 네이버 장소 ID ↔ 밥줄 식당 ID 매핑을 정한다.
- 일반 식당 DTO에 주소·위도·경도·층을 제공하고 기존 식당의 위치 자료를 채울 절차가 필요하다. 검색 결과를 스크래핑하거나 주소 문자열에서 좌표를 추측하지 않는다. 네이버 Client Secret은 서버에만 둔다.
- 식당 변경 UI가 제거된 상태에서 여러 매장을 소유한 계정의 최종 관리 방식이 필요하면 기획과 먼저 합의한다.

## 계약 수용 테스트용 데이터 요청

아래는 **별도 테스트 DB**에 필요한 시나리오다. 현재 미지원 API가 완성되었다고 가정하거나 실제 운영 데이터를 변경하는 요청이 아니다.

1. 점주 A와 B 및 각각 소유한 식당 1개 이상. 다른 점주 식당 수정/제보 관리 차단 확인에 사용한다. 복수 매장 계정이 지원 대상이면 별도 점주 C와 매장 2개를 추가한다.
2. 식당 영업 일정 4종: 일반 주간 영업, 자정 넘김, 정기 휴무, 특정 날짜 휴무 및 임시 영업 변경. 시작=종료의 정책과 한국 시간 경계 사례도 제공한다.
3. 한 식당의 서비스형 혜택 3단계. 미진행·진행·중지·게시 종료 상태, 여러 단계 동시 진행, 중복 진행 요청을 검사할 수 있게 한다. 500P·1,500P·4,500P 비용, 종료일 있음/없음, 요일/시간 제한 없음, 복수 구간, 다음 날 종료를 포함한다. 퍼센트 할인은 별도 기존 혜택으로 1개 둬서 데이터가 혼동되지 않는지 확인한다.
4. 한 식당에 손님·점주 제보 최소 12건. 설명 있음/없음, 같은 시각의 서로 다른 ID, 최신순 한 페이지를 넘는 목록을 포함한다. 페이지 크기는 계약 확정값에 맞춘다.
5. 4주 분석용 제보는 최소 4개의 같은 요일을 포함하고, 같은 시간대에서 여유 우세(예: 3/1/1), 보통 우세(1/3/1), 혼잡 우세(1/1/3), 동률이며 최근 상태가 다른 사례를 각각 만든다. 숫자는 여유/보통/혼잡 제보 수다.
6. 분석 경계 데이터: 제보 없는 시간, 여유만 있는 시간, 28일 시작 경계 전후, 미래/유효하지 않은 시각 거부, 한국 시간 자정 전후. 동일 시각 동률 및 UNKNOWN 처리도 검증한다.
7. 앱 계정 변경/재실행, 네트워크 실패, 서버 성공 후 응답 또는 기기 저장 실패, 인증 만료를 포함한다. 로컬 기록과 서버 기록이 중복 제출되지 않아야 한다.
8. 손님별 최초 지급 전/후, 동일 제보 보상 재시도, 잔액 부족/충분, 미사용·사용·만료 쿠폰, 게시 취소/종료 후 보유 쿠폰, 사용/만료 후 재다운로드와 재차감 자료가 필요하다. 72시간 경계 직전/정각, 한국 시간 사용 구간 직전/종료 정각도 포함한다.
9. 동시 다운로드·동시 사용·차감 성공 후 발급 실패·성공 응답 유실을 검사한다. 실제 위치/개인정보를 넣지 않은 독립 테스트 자료를 사용하고 기존 계정·매장 데이터는 변경하지 않는다.

쿠폰/포인트, 손님 체류 증명, 프로필 동기화 등 공통 요청은 [BACKEND_REQUIREMENTS.md](./BACKEND_REQUIREMENTS.md)에 이어서 정리되어 있다.

## 쿠폰 추가 작업의 검증 범위

- 기기 쿠폰 저장소의 단위 테스트 **20개**, 일정 판정의 단위 테스트 **25개**를 통과했다. 최초 지급/제보 적립 멱등성, 비용과 잔액, 계정·서버 분리, 취소·종료 후 보유 조건, 정확한 72시간 만료, 동시 요청, 손상 상태 거부, 파일 교체 실패 복구, 요일·시간·자정 경계를 포함한다.
- 전체 프론트 회귀 테스트 **148개**, TypeScript 검사, Android Hermes export(811개 모듈)를 통과했다. 파일 선택용 DocumentPicker를 포함한 Android x86_64 개발 APK를 빌드하고 기존 앱 데이터를 지우지 않는 업데이트 설치를 완료했다. 배포용 독립 실행 APK/실제 서버 쿠폰 거래 검증과는 구분한다.
- 390×844 Android 앱에서 별도 가상 계정·가상 API·별도 저장 범위로 500P 발행 → 손님 다운로드 → 중복 다운로드 버튼 비활성화 → 사용 완료 → 재다운로드/재차감 → 발행 취소 후 보유 쿠폰 유지까지 확인했다. 지갑은 1,000P → 500P → 0P로 변했고, 가상 제보 성공 응답 후 +1,000P를 확인했다. 실제 GPS나 실제 서버 제보는 사용하지 않았다.
- 내 파일 선택기로 테스트 이미지를 선택·저장했고 앱 재시작 후 사진, 포인트 원장, 두 쿠폰의 사용 여부 및 각각 정확히 72시간의 유효기간이 복원됐다. 발행 옵션의 500P 프리셋, 요일·시간 제한 없음 비활성화, 시간 구간 추가와 입력 배치를 화면 캡처로 확인했으며 긴 시간 입력 라벨을 짧게 수정했다. 사진 선택의 분할 번들 로딩 오류를 고친 뒤 네이티브 선택기를 다시 검증했다.
- 검수 후 가상 계정의 쿠폰/프로필/점주 설정과 테스트 사진 복사본만 정리하고 원래 개발 연결 설정을 복원했다. 기존 서버·계정·사진 원본은 변경하지 않았다. 백엔드와 Metro는 유지했으며 앱은 실제 로그인 진입 화면으로 돌아갔다.
- 시간대 밖 사용 차단, 정확한 72시간 경계, 만료 후 재다운로드, 저장 실패·동시 요청은 고정 시각/모의 저장소 자동 테스트로 검증했다. 에뮬레이터에서 3일을 실제 대기하거나 휴대폰 시각을 변경한 검증은 아니다.
- 현재 실제 백엔드에 포인트·쿠폰·요일별 단계 프로모션 API가 없다는 점을 최신 원격/로컬 코드에서 재확인했다. 새로운 서버 수용 테스트나 실제 결제 검증을 수행한 것이 아니다.

## 이전 점주 UI 변경의 검증 결과와 남은 수용 기준

- 전체 TypeScript 검사와 회귀 테스트 **70개** 통과. 기존 고객 22개, 영업시간 5개, 4주 집계 11개, 입력 폼 10개, 저장 계층 16개, 화면 상태·경쟁 조건 6개를 검증했다.
- Android Hermes 번들 export 통과(801개 모듈). 새 배포 APK를 발행한 것은 아니다.
- 설치된 Android 앱의 390×844 화면에서 실제 계정과 분리한 가상 점주/메모리 API 응답으로 검수했다. 이 검수에서는 실제 백엔드에 등록·제보 요청을 보내지 않았고 GPS 수집·권한 변경도 하지 않았다.
- 첫 진입 1단계, 영업시간 묶음/정기 일요일 휴무 선택, 등록 후 2단계 이동, 저장 알림 제거, 제목 옆 수정 버튼 1개와 3단계 스크롤을 확인했다.
- 1·2단계 진행 → 제보 화면에 두 혜택 반영 → 1단계 중지, 추가 설명 저장 → 제보 목록 반영을 확인했다. 앱 프로세스를 다시 시작한 뒤 2단계 진행 상태, 제보 설명, 일요일 휴무, 날짜별 영업 변경이 복원됐다.
- My에만 로그아웃, 시간/주소 분리 화면, 날짜 선택·영업 선택 및 시간 입력 화면을 캡처해 잘림/스크롤 동작을 확인했다. 최근 4주 그래프의 요일 선택·시간별 세 색상·숫자 없음도 별도 가상 관측값으로 확인했다.
- 기존 서버 연결 코드는 유지했지만 이번 변경의 실제 서버 수용 테스트 및 손님 전체 목록/실제 게시/공유 일정/매장 전체 4주 분석은 완료하지 않았다. 다음은 서버 계약 확정 후의 수용 기준이다.

- 빈 점주 계정 로그인 → 1단계 바로 진입 → 앱 내 네이버 검색 → 이름/주소/시간/휴무 입력 → 서버 식당 등록 → 2단계 저장.
- 프로모션 제목 옆 수정 1개, 3단계 발행 조건 설정·진행/중지, 제보 화면과 같은 기기의 손님 화면 표시, 앱 재실행 후 복원. 이전 상태 토글과 새 쿠폰 발행 흐름의 검증을 구분한다.
- 추가 설명과 함께 점주 제보 → 실제 서버 혼잡도 반영 → 기기 최신순 목록/설명 복원. 서버 요청은 기존 `{ level }` 계약을 유지하는지 확인.
- My에만 로그아웃이 존재하는지, 시간 수정이 주소/이름을 바꾸지 않는지, 위치 수정이 시간을 바꾸지 않는지 확인.
- 정기 휴무 및 특정 날짜 휴무/영업 선택·시간 유효성·저장/재진입. 손님 화면에서는 기본 영업시간만 공유되는 범위를 확인.
- 최근 4주만 표시, 7개 요일과 24시간 스크롤, 최빈값/최근 제보 동률, 여유 0/데이터 없음 구분, 막대 위 숫자 없음, 내 기기 제보 범위 표시 확인.
- 기존 실제 계정/식당 데이터와 분리된 임시 서버 및 가상 UI 자료를 사용하고, 가상 자료는 실서비스 전체 분석 검증과 구분한다.

서버가 요청을 처리한 뒤 응답 자체가 유실된 경우의 중복 생성/제보 방지는 현재 계약만으로 완전 보장할 수 없다. 서버의 멱등성 키 또는 요청 결과 재조회 계약을 함께 검토한다.

## 이전 검증 이력

2026-10-07~08 이전 버전에서 임시 H2 서버와 Android 앱을 이용해 점주 로그인·식당 등록·혼잡도 제보·퍼센트 할인 관리·시간 수정·기기 설정 복원을 확인했다. 당시의 최근 7일 평균/선 그래프와 할인 등록 화면은 이번 피드백에서 제거되었으므로 그 검증을 새 점주 UI의 완료 근거로 재사용하지 않는다. 로고·하단 SVG 아이콘 교체 결과는 유지되며, 새 화면의 검증 결과는 별도로 갱신해야 한다.
