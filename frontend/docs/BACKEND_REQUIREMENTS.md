갱신일: 2026-10-08. `origin/backend-a: 4a973fe`, `origin/backend-b: ab36c09`를 fetch하여 로컬 Controller/DTO와 비교했다. 아래 미지원 항목은 이 버전 기준이다.

점주 UI의 추가 요구사항과 연결 범위는 [OWNER_UI.md](./OWNER_UI.md)에 정리했다. 2026-10-08 피드백은 사용자 승인에 따라 프론트 UI와 기기 저장까지 구현하며 서버 계약은 변경하지 않는다. 단계별 쿠폰 발행·손님 포인트·다운로드/사용은 **동일 기기 안의 계정 간 기능**이고 실제 서버 게시·결제가 아니다. 추가 설명과 최근 4주 최빈값 그래프도 현재 이 기기에 저장된 점주 본인의 성공 제보만 사용한다. 전체 매장 분석으로 표시하지 않는다. 휴무·영업 일정, 28일 원시 제보 또는 상태별 집계, 최신순 제보 목록·설명 API는 해당 문서에서 협의한다.

## 이미 있는 기능 — 새 API 요청 대상 아님

- 이메일·비밀번호 회원가입/로그인, 내 계정 조회: `/api/auth/signup`, `/login`, `/me`.
- 식당 목록/상세, 혼잡도 제보/집계, 시간별 혼잡도 차트.
- 활성 프로모션 조회.
- GPS 체류 샘플 기반 주변 후보 추천: `POST /api/v1/location/stays/recommendations`.
- 기존 차트 API 데이터는 프론트에서 막대로 표현한다. 해당 API의 최대 168시간 데이터와 별도 기기 기록의 4주 집계는 서로 다른 범위다.
- Android 위치·알림 권한 팝업은 운영체제 기능이다. 권한 요청 자체에 백엔드 API는 필요 없다.

## 우선 협의할 요구사항

현재 로그인 식별자는 이메일이며 닉네임은 앱 표시 이름이다. 독립된 문자열 아이디로 가입/로그인하려면 별도 필드, 중복 검사, 저장·조회 및 로그인 계약을 백엔드와 먼저 합의해야 한다. 현재 UI는 ‘이메일 (로그인 아이디)’와 ‘닉네임 (앱 표시 이름)’으로 이를 안내한다.

### 1. 식당 위치와 거리

- 식당 등록/수정/조회 DTO에 위도·경도·층 정보를 제공하고, 기존 매장 좌표를 채우는 절차가 필요하다. 도메인에는 위치 필드가 있지만 현재 일반 식당 DTO에는 없다.
- 홈의 거리순 정렬과 ‘걸어서 N분’, 지도 보기에 사용할 데이터 계약을 정해야 한다. 체류 후보 API의 직선거리와 도보 시간은 다르므로 임의로 환산하지 않는다.
- 완료 기준: 실제 등록 매장이 GPS 후보에 나타나고, 홈에 표시할 거리/도보 시간의 단위와 제공 범위가 명확하다.

### 2. 상세 화면의 최근 제보 / 나의 제보 내역

- 식당별 최근 제보 목록: 표시용 닉네임, 혼잡도, 제보 시각, 페이지 처리 필요.
- 인증 사용자 본인의 제보 내역: 식당 이름/ID, 혼잡도, 제보 시각, 날짜별 조회 또는 페이지 처리 필요.
- 현재 집계 API와 제보 생성 응답만으로는 Figma의 개별 제보 목록과 재로그인 후 전체 내역을 구성할 수 없다. 손님 제보 목록은 해당 로그인 세션에서 성공한 항목만 보관하며, 점주 목록은 성공한 제보와 추가 설명을 기기에 보관한다. 포인트 중복 적립 방지 기록을 전체 제보 목록 API의 대체로 사용하지 않는다.
- 공개 닉네임 표시 정책과 개인 정보 노출 범위도 합의한다.

### 3. 포인트와 쿠폰 — 확정 정책 및 현재 범위

**현재 서버에는 포인트·쿠폰 기능이 없다.** 최신 `backend-a 4a973fe`, `backend-b ab36c09` 및 로컬 `CrowdService.saveStatus`를 확인하면 제보는 혼잡도 기록 저장 후 응답을 반환할 뿐, 보상을 지급하지 않는다. 백엔드 개발 시드 문서도 포인트 잔액/적립/차감과 쿠폰 발급/보유/사용/만료를 별도 API 필요 항목으로 명시한다. 기존 프로모션의 할인율·시작/종료 일시·enabled는 쿠폰 거래 모델이 아니다.

사용자가 승인한 기기 내 구현 정책:

- 손님 지갑 최초 생성 때 **1,000P 한 번 지급**, 성공한 손님 제보의 서버 응답 **제보 ID당 1,000P 한 번 적립**. 재로그인·재시도로 같은 지급을 반복하지 않는다.
- 점주는 비용을 **500P 이상, 500P 단위**로 설정한다. 3,000P 상한은 없다. **1P = 1원**은 혜택의 기획상 환산 기준이며 현금성 잔액, 환급, 결제 또는 실제 서비스 가격을 검증하는 기능이 아니다.
- 식당에서 멀리 있어도 다운로드할 수 있다. 사용 요일·시간 밖에서도 다운로드 가능하며, 게시 유효성·잔액·중복 보유 여부를 검사한다.
- 받은 쿠폰의 유효기간은 **다운로드부터 정확히 72시간**이다. 점주 게시의 종료일/종료일 없음과 별개다.
- 같은 발행 ID의 미사용·미만료 쿠폰을 이미 보유하면 추가 발급·차감하지 않는다. 사용 또는 만료 뒤에는 게시가 유효할 경우 **다시 다운로드하고 다시 차감**한다.
- 발급 시 혜택 문구, 요일·시간 조건, 비용을 복사해 보존한다. 게시 취소/종료는 신규·재다운로드만 차단하고, 이미 받은 쿠폰은 72시간 안에서 보존된 사용 요일·시간대로 계속 유효하다.
- 사용은 미사용 여부·72시간·사용 요일/시간으로 판정한다. 임의의 사용 GPS 제한은 추가하지 않는다. 실제 점주 승인·결제는 아직 없다.

저장·표시 범위:

- 동일 기기의 앱 문서 영역에서 서버별로 발행 기록을 공유하므로 점주에서 발행 후 손님 계정으로 로그인하여 확인할 수 있다. 지갑은 사용자 ID+이메일별로 분리한다. 다른 기기에는 공유하지 않는다.
- 포인트 거래 내역·차감·쿠폰 생성/사용 상태를 같은 파일에 함께 저장한다. 직렬 처리와 임시 파일 교체를 사용하며 손상된 기록을 빈 지갑으로 덮어쓰지 않는다. 기기 저장 성공과 서버 거래 성공을 구분한다.
- 이전 단계별 혜택 문구는 보존하지만 기존 진행 토글을 쿠폰으로 자동 변환·발행하지 않는다. 점주가 새 발행 조건을 확인해야 한다.
- 앱 데이터 삭제·재설치·다른 기기 복원·오프라인 위변조 방지를 보장하지 않는다. 현재는 기기 시각을 사용한다. 실제 서비스 지갑/보상의 진실은 서버가 관리해야 한다.

백엔드 팀과 합의할 계약(경로는 확정 후 연결):

1. **프로모션 발행 모델:** 식당 소유권, 발행 ID/버전, 1~3단계, 서비스형 혜택 문구, 게시/취소 상태, 게시 종료일 또는 없음, 사용 요일·복수 시간 구간 또는 제한 없음, 500P 단위 비용. 퍼센트 할인과 별도 모델로 구분한다.
2. **지갑·거래 내역:** 잔액과 지급/차감 원장, 최초 1,000P 지급 기록, 검증된 제보 ID와 보상 거래 연결. 최초 지급과 제보 적립을 원자적·멱등적으로 처리하고 서버 성공 결과를 조회할 수 있어야 한다.
3. **발급·내 쿠폰:** 발행 유효성, 잔액, 중복 보유를 서버에서 검사하고 차감과 발급을 한 거래로 완료한다. 다운로드 시각·정확한 72시간 만료, 보존한 혜택/사용 조건/비용, 사용 시각·상태를 제공한다. 같은 쿠폰 동시 다운로드/사용·재시도·응답 유실 시 중복 차감이나 중복 사용이 없어야 한다.
4. **서버 시간·조건 판정:** `Asia/Seoul` 기준 게시 종료일/요일/시간, 자정 넘는 구간, 시작 포함·종료 제외 경계를 정의한다. 쿠폰 만료는 서버 다운로드 시각+72시간으로 계산하고 기기 시각 변경으로 연장하지 않는다. 게시 취소가 보유 쿠폰의 조건을 소급 무효화하지 않도록 한다.
5. **보상 자격·사용 확인:** GPS 체류 증명, 사용자/식당 결합, 재사용 방지 및 중복 제보 보상 제한을 서버에서 검증한다. 점주 제보와 손님 보상을 구분한다. 쿠폰 사용을 손님 확인만으로 처리할지 점주 확인/코드/QR 등이 필요한지 먼저 결정한다. 프론트의 버튼 제한이나 로컬 사용 완료를 실제 매장 승인으로 간주하지 않는다.
6. **오류·동기화·이전:** 잔액 부족, 만료, 이미 사용, 중복 보유, 게시 취소, 소유권 위반, 인증 만료, 동시 충돌 오류를 구분한다. 기기 테스트 기록을 서버로 옮길지, 새 서비스 지갑과 분리할지 합의하고 자동 업로드나 자동 실지급은 하지 않는다.

### 4. 회원가입 동의와 이메일 인증

- 필수/선택 약관 본문 및 버전, 동의 시각, 선택 마케팅 동의 저장 계약이 필요하다. 현재 체크박스는 프론트 진행 조건이며 서버에 저장되지 않는다.
- 설계의 이메일 인증을 유지하려면 코드 발송/검증, 만료·재전송·시도 제한, 가입 시 검증 증명 확인이 필요하다. 현재 이메일 형식 검사만 있고 소유권 인증은 없다.
- 닉네임은 회원가입에서 입력한다. 인증번호 기능과 닉네임 입력은 별개이며 하나로 대체해 완료로 간주하지 않는다.

- 2026-10-08 `origin/backend-b` 최신 `ab36c09` 및 로컬 Controller를 확인했다. 이메일 signup/login/me만 제공하며 개발 시드 문서도 Google/네이버 소셜 로그인을 제외한다.

- 연동 계약: 제공사별 로그인 증명 종류와 서버 교환 경로, 검증 실패 응답, 기존 사용자 Bapjul JWT 발급 응답, 신규 사용자 닉네임·약관·역할 입력 완료 방식. 현재 이메일 로그인 `AuthResponse`와 동일한 세션 형태로 연결하는 것을 권장한다.
- Google/네이버 인증 지원 여부, 모바일 리다이렉트/클라이언트 설정, 토큰 검증·계정 연결·신규 계정 역할/닉네임 등록 계약을 정해야 한다.
- 현재 버튼은 준비 중 안내만 표시한다. 지원하지 않는다면 버튼 노출 변경은 디자인/기획 합의 후 결정한다.

### 6. 체류 증명과 제보 권한

- 현재 앱의 5분 체류 검사를 서버 제보 요청에서도 검증할 수 있는 계약이 필요하다. 앱에서 버튼을 제한하는 것만으로 서버 요청 위조를 막을 수 없다.
- 후보 식당·사용자에 결합된 만료 가능한 체류 증명 등 검증 방법, 반복 제보/보상 제한을 협의한다. 현재 프론트의 제보 ID별 1,000P 기기 적립은 부정 제보 방지나 서버 보상 지급의 증거가 아니다. 구체적 API 경로는 제안 확정 전 임의로 정하지 않는다.
- 위치 샘플 보관/삭제 정책과 사용자 안내를 확정한다. 실제 GPS 수집 테스트는 별도 사용자 동의 후 수행한다.

## 배포 전 계약

- HTTPS 배포 주소, 공통 오류 형식, 토큰 만료 및 재로그인/갱신 정책.
- 알림 UI에 안내된 대기·프로모션 알림을 실제 제공한다면 기기 토큰 등록/삭제 및 알림 발송 계약. Android 체류 관찰 중 알림은 로컬 알림이며 서버 푸시와 별개이다.

## 2026-10-08 손님 피드백 후 우선 연동 항목

1. **전체 거리순:** 일반 식당 응답에는 아직 위도·경도/거리가 없다. 앱은 최신 체류 후보의 확인된 거리만 사용하고 나머지는 ‘거리 확인 전’으로 뒤에 둔다. 전체 목록 거리 정렬을 완료하려면 매장 좌표와 현재 위치 기반 거리 조회 계약이 필요하다. 원본 GPS를 임의 저장하거나 직선거리를 도보 거리로 표시하지 않는다.
2. **앱 내 네이버 검색:** 현재 React Native 앱 안의 WebView에서 네이버가 제공하는 검색 결과를 표시한다. 밥줄 목록과 별개의 네이버 화면이며 인증 토큰·GPS를 전달하지 않는다. 네이버 검색 결과를 밥줄 식당/혼잡도와 통합하려면 서버 검색 프록시, 네이버 장소 ID ↔ 밥줄 식당 ID 매핑, 오류·호출 제한 처리가 필요하다. 네이버 Client Secret은 반드시 서버에 보관한다. WebView에서 결과를 추출하거나 네이버 결과를 밥줄의 가입 식당으로 가장하지 않는다.
3. **쿠폰/포인트:** 사용자 승인 정책에 따라 같은 기기 안에서 발행·다운로드·적립·차감·사용을 구현한다. 실제 서버 연결은 여전히 활성 할인 안내 조회뿐이며, 그 할인 안내를 자동으로 쿠폰화하지 않는다. 서버 연동은 위 3절의 발행/지갑/쿠폰 모델, 체류 보상 검증, 원자성·멱등성·서버 시간 계약이 필요하다.
4. **근처 식당 제보:** 앱의 최신 GPS 60초 이내·5분 체류·최대 50m 후보 제한과 서버의 제보 권한을 결합해야 한다. 현재 `{level}`만으로 제보 POST가 수락됨을 임시 DB 테스트에서 확인했다. 사용자/식당/만료시각에 연결된 체류 증명과 재사용 방지 없이는 부정 제보·포인트 적립을 막을 수 없다.
5. **프로필 동기화:** 로컬 사진/닉네임 저장과 계정 프로필 변경을 구분한다. 서버 API 제공 후 업로드와 재로그인/다른 기기 조회를 연결한다.

수용 테스트용 데이터: 식당 7개(목록 3→6→7), 같은 건물/50m 경계 안팎 후보, 기존 활성 할인 2개·만료/예정/중지 상태, 서비스형 프로모션 3단계, 쿠폰 미보유/보유/사용/만료 손님이 필요하다. 비용 500P·1,500P·4,500P, 잔액 부족/충분, 최초 지급·제보 적립 전후와 재시도를 준비한다. 게시 취소/종료 후 보유 쿠폰, 72시간 만료 직전/정각, 한국 시간의 요일·복수 시간 구간·자정 넘김, 사용/만료 후 재다운로드와 재차감도 포함한다. 동시 요청·응답 유실·저장 실패를 별도 테스트 DB에서 검사하며 기존 사용자 데이터는 변경하지 않는다. 현재 로컬 성공을 서버 쿠폰/포인트 수용 테스트 통과로 판정하지 않는다.

이번 쿠폰 작업의 로직 검증: 모의 파일 저장소/고정 시각으로 저장소 테스트 20개와 일정 테스트 25개를 통과했다. 새 화면 전체 회귀 수와 APK 설치·네이티브 발행→손님 다운로드→사용 검증 결과는 진행 완료 후 별도로 갱신한다. 아래 메모리 서버 및 기존 화면 검증은 이전 작업 이력이다.

별도 메모리 H2의 실제 백엔드 JAR 검증: 가입/로그인/me, 식당 7개 조회, 활성 할인만 노출, 없는 식당 404, 제보 후 집계 반영 등 16개 확인. 테스트 서버 종료 시 계정과 데이터가 소멸하며 기존 DB는 변경하지 않았다. 실제 GPS 수집·OS 알림 전달 검증은 수행하지 않았다.

프론트 검증: TypeScript 및 단위 테스트 22개, Android Hermes 번들, x86_64 에뮬레이터용 APK 빌드/설치 통과. 별도 가상 데이터 화면에서 390×844 기준 손잡이 드래그 펼침/접기·내부 스크롤·3→6→7개, 후보 거리 12m→45m→거리 미확인 순서, My 오른쪽 위 로그아웃, 시스템 사진 선택·자르기·저장·재진입 복원, 가상 5분 체류 팝업→근처 후보 화면을 확인했다. 앱 내부 네이버 지도에서 실제 `pizza` 검색 결과도 표시됨을 확인했다. 이 UI 검수의 가상 제보 후보는 실제 GPS 검증이나 서버 체류 증명의 대체가 아니다.

## 이번 재검토의 확인 범위

- 현재 화면/인증/권한 코드와 Controller/DTO를 재확인했다. 기존 에뮬레이터 캡처 및 이전 기능 검증과 구분한다.
- 이번에는 권한을 새로 허용하거나 계정을 생성하지 않았으며, 전체 신규 스크린샷 비교를 다시 수행한 것은 아니다. 픽셀 단위 완성 판정은 보류한다.
- 가입 → 필수 약관 → 역할 선택 → 서버 가입 → 가입 완료 → ‘바로 로그인’ → 서버 로그인 → 역할에 맞는 홈이 현재 흐름이다. 가입 직후 입력 정보는 이 단계의 메모리에만 두며, 나중에 로그인/뒤로/로그인 성공 시 비밀번호를 비운다. 로그인 실패 시 계정을 다시 생성하지 않고 로그인만 재시도한다. 시연용 계정 우회는 없다.
- 약관 화면에서 뒤로 갔다가 다시 진입하면 체크 상태가 초기화되는 현재 동작도 사용성 검토 대상이다.
- 초기 재검토에서 발견한 알림 응답 타입 오류는 후속 UI 작업에서 iOS 응답 상태를 명시적으로 정규화해 수정했다. `tsc --noEmit` 재검사는 통과했다. iOS 실제 기기 검증을 완료했다는 의미는 아니다.
- 후속 UI 작업에서 상세 그래프를 실제 차트 데이터의 상태별 막대로 구현했다. 제보 선택지·확인 팝업·My 배치도 정돈했다. 개별 제보 목록과 포인트/쿠폰 데이터 API 요청은 여전히 유효하다.
