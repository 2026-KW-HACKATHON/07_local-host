## 이미 있는 기능 — 새 API 요청 대상 아님

- 이메일·비밀번호 회원가입/로그인, 내 계정 조회: `/api/auth/signup`, `/login`, `/me`.
- 식당 목록/상세, 혼잡도 제보/집계, 시간별 혼잡도 차트.
- 활성 프로모션 조회.
- GPS 체류 샘플 기반 주변 후보 추천: `POST /api/v1/location/stays/recommendations`.
- 차트가 현재 텍스트 목록으로 보이는 것은 프론트 UI 미완성이며 백엔드 차단 사유가 아니다.
- Android 위치·알림 권한 팝업은 운영체제 기능이다. 권한 요청 자체에 백엔드 API는 필요 없다.

## 우선 협의할 요구사항

현재 로그인 식별자는 이메일이며 닉네임은 앱 표시 이름이다. 독립된 문자열 아이디로 가입/로그인하려면 별도 필드, 중복 검사, 저장·조회 및 로그인 계약을 백엔드와 먼저 합의해야 한다. 현재 UI는 ‘이메일 (로그인 아이디)’와 ‘닉네임 (앱 표시 이름)’으로 이를 안내한다.

### 1. 식당 위치와 거리

- 식당 등록/수정/조회 DTO에 위도·경도·층 정보를 제공하고, 기존 매장 좌표를 채우는 절차가 필요하다. 도메인에는 위치 필드가 있지만 현재 일반 식당 DTO에는 없다.
- 홈의 거리순 정렬과 ‘걸어서 N분’, 지도 보기에 사용할 데이터 계약을 정해야 한다. 체류 후보 API의 직선거리와 도보 시간은 다르므로 임의로 환산하지 않는다.
- 완료 기준: 실제 등록 매장이 GPS 후보에 나타나고, 홈에 표시할 거리/도보 시간의 단위와 제공 범위가 명확하다.

### 2. 상세 화면의 최근 제보 / 나의 제보 내역

- 식당별 최근 제보 목록: 표시용 닉네임, 혼잡도, 제보 시각, 페이지 처리 필요.
- 인증 사용자 본인의 제보 내역: 식당 이름/ID, 혼잡도, 제보 시각, 날짜별 조회 또는 페이지 처리 필요.
- 현재 집계 API와 제보 생성 응답만으로는 Figma의 개별 제보 목록과 재로그인 후 전체 내역을 구성할 수 없다. 현재 앱 내 제보 내역은 해당 로그인 세션에서 성공한 항목만 보관한다.
- 공개 닉네임 표시 정책과 개인 정보 노출 범위도 합의한다.

### 3. 포인트와 쿠폰

- 내 포인트 잔액/적립·차감 내역, 제보 보상 지급 결과가 필요하다.
- 프로모션별 쿠폰 교환 비용, 혜택, 유효기간, 발급 가능 상태가 필요하다. 현재 할인율 프로모션과 Figma의 정액 할인 쿠폰은 계약이 다르다.
- 쿠폰 발급/교환, 내 쿠폰 목록, 사용/만료 상태 조회가 필요하다.
- 차감과 쿠폰 발급은 서버에서 원자적으로 처리하고 중복 요청을 방지해야 한다. 잔액 부족/만료/중복 교환 오류를 정의한다.
- Figma의 보상·차감 숫자를 고정해 실제 성공으로 표시하지 않는다. 서버 확정 결과로 적립/교환 완료 팝업을 표시한다.

### 4. 회원가입 동의와 이메일 인증

- 필수/선택 약관 본문 및 버전, 동의 시각, 선택 마케팅 동의 저장 계약이 필요하다. 현재 체크박스는 프론트 진행 조건이며 서버에 저장되지 않는다.
- 설계의 이메일 인증을 유지하려면 코드 발송/검증, 만료·재전송·시도 제한, 가입 시 검증 증명 확인이 필요하다. 현재 이메일 형식 검사만 있고 소유권 인증은 없다.
- 닉네임은 회원가입에서 입력한다. 인증번호 기능과 닉네임 입력은 별개이며 하나로 대체해 완료로 간주하지 않는다.

### 5. 소셜 로그인

- 2026-10-08 `origin/backend-b` 최신 `ab36c09` 및 로컬 Controller를 확인했다. 이메일 signup/login/me만 제공하며 개발 시드 문서도 Google/네이버 소셜 로그인을 제외한다.

## 2026-10-08 손님 피드백 후 우선 연동 항목

1. **전체 거리순:** 일반 식당 응답에는 아직 위도·경도/거리가 없다. 앱은 최신 체류 후보의 확인된 거리만 사용하고 나머지는 ‘거리 확인 전’으로 뒤에 둔다. 전체 목록 거리 정렬을 완료하려면 매장 좌표와 현재 위치 기반 거리 조회 계약이 필요하다. 원본 GPS를 임의 저장하거나 직선거리를 도보 거리로 표시하지 않는다.
2. **앱 내 네이버 검색:** 현재 React Native 앱 안의 WebView에서 네이버가 제공하는 검색 결과를 표시한다. 밥줄 목록과 별개의 네이버 화면이며 인증 토큰·GPS를 전달하지 않는다. 네이버 검색 결과를 밥줄 식당/혼잡도와 통합하려면 서버 검색 프록시, 네이버 장소 ID ↔ 밥줄 식당 ID 매핑, 오류·호출 제한 처리가 필요하다. 네이버 Client Secret은 반드시 서버에 보관한다. WebView에서 결과를 추출하거나 네이버 결과를 밥줄의 가입 식당으로 가장하지 않는다.
3. **쿠폰/포인트:** 현재 활성 할인 안내 조회만 실제 연결된다. 할인 안내가 있다는 이유로 ‘쿠폰 발급 가능/보유’를 만들지 않는다. 식당별 발급 가능 쿠폰/발급 POST/내 쿠폰 GET/포인트 잔액 및 제보 적립 결과, 중복 발급·만료·잔액 부족·인증 만료 오류 계약이 필요하다. 제보 저장과 보상 지급, 교환과 차감은 서버에서 중복 방지 및 원자성을 보장한다.
4. **근처 식당 제보:** 앱의 최신 GPS 60초 이내·5분 체류·최대 50m 후보 제한과 서버의 제보 권한을 결합해야 한다. 현재 `{level}`만으로 제보 POST가 수락됨을 임시 DB 테스트에서 확인했다. 사용자/식당/만료시각에 연결된 체류 증명과 재사용 방지 없이는 부정 제보·포인트 적립을 막을 수 없다.
5. **프로필 동기화:** 로컬 사진/닉네임 저장과 계정 프로필 변경을 구분한다. 서버 API 제공 후 업로드와 재로그인/다른 기기 조회를 연결한다.

수용 테스트용 데이터: 식당 7개(목록 3→6→7), 같은 건물/50m 경계 안팎 후보, 활성 할인 2개·만료/예정/중지 각 상태, 쿠폰 미보유/보유/사용/만료 사용자, 제보 적립 전후·중복 제보·잔액 부족이 필요하다. 쿠폰/포인트 API가 없는 현재 버전에서는 해당 성공 시나리오를 완료로 판정하지 않는다.
